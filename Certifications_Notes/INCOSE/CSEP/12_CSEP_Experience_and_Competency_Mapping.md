# 12 — CSEP Experience and Competency Mapping

## 1. Purpose of This Module

This module provides a practical framework for organizing professional experience and connecting it to systems engineering competencies.

It is designed to help you:

* Build a structured record of relevant experience.
* Distinguish systems engineering work from adjacent technical work.
* Identify evidence of systems thinking, requirements engineering, architecture, integration, verification, validation, risk management, and life-cycle management.
* Write accurate experience descriptions for applications, CVs, interviews, and professional development.
* Identify competency gaps and create a development plan.
* Prepare clear examples that explain your individual contribution.

**Important:** This is a self-assessment framework, not an official INCOSE scoring rubric or a guarantee of CSEP eligibility. Certification eligibility, experience definitions, application requirements, references, and examination rules can change. Always consult the current official INCOSE certification materials before applying.

## 2. Understand the Difference Between Certification Eligibility and Competency

These concepts are related but distinct.

### Certification eligibility

Eligibility is determined by the applicable certification program's current rules. It may include education, qualifying experience, application documentation, references, examination, and other requirements specified by INCOSE.

Do not assume that:

* Every technical job automatically qualifies as systems engineering experience.
* Every project activity counts equally.
* A completed course or certificate replaces required professional experience.
* A self-assessment spreadsheet establishes official eligibility.

### Competency

Competency is the demonstrated ability to apply knowledge, judgment, and skills to perform work effectively.

Examples include:

* Eliciting and analyzing stakeholder needs.
* Developing and managing requirements.
* Evaluating architecture alternatives.
* Coordinating interfaces and integration.
* Planning verification and validation.
* Managing technical risks and changes.
* Communicating trade-offs to stakeholders.

A person may understand a topic theoretically without having demonstrated it in a professional project. Conversely, a person may have performed relevant work without using formal systems engineering terminology.

The purpose of mapping is to document what you actually did, what decisions you influenced, and what evidence supports the claim.

## 3. A Practical Competency Framework

Use the following categories to organize experience. They are a study and reflection framework, not a representation of an official INCOSE competency scoring scheme.

| Category                     | Evidence to look for                                                                  |
| ---------------------------- | ------------------------------------------------------------------------------------- |
| Stakeholder needs            | Interviews, workshops, operational analysis, stakeholder concerns                     |
| Requirements engineering     | Requirements elicitation, analysis, allocation, traceability, change control          |
| System architecture          | Functional decomposition, logical or physical architecture, trade studies             |
| Design and interfaces        | Interface definition, technical specifications, design decisions                      |
| System analysis              | Modeling, simulation, feasibility analysis, quantitative evaluation                   |
| Technical planning           | Life-cycle plans, technical schedules, resource and dependency planning               |
| Risk and opportunity         | Risk identification, analysis, mitigation, monitoring                                 |
| Configuration and change     | Baselines, version control, change requests, impact analysis                          |
| Integration                  | Integration planning, interface checks, incremental assembly                          |
| Verification                 | Requirement-based test planning, inspection, analysis, test evidence                  |
| Validation                   | Evaluation of whether the system meets stakeholder needs in its intended context      |
| Technical assessment         | Reviews, metrics, audits, performance assessment                                      |
| Specialty engineering        | Safety, reliability, security, maintainability, human factors, supportability         |
| Life-cycle management        | Operations, maintenance, upgrades, transition, retirement                             |
| Communication and leadership | Technical coordination, decision records, issue resolution, stakeholder communication |

A single activity may provide evidence for multiple categories. For example, an interface review may involve requirements, architecture, risk, integration, and verification.

Avoid double-counting the same work as several separate experiences merely because it touches multiple categories. Describe the actual activity once and map its evidence to relevant competencies.

## 4. What Counts as Useful Evidence?

Strong experience records explain both the work performed and the result.

### Weak description

“Worked on a monitoring system.”

This does not establish the person's role, complexity of the work, engineering methods, decisions, or outcome.

### Stronger description

“Analyzed monitoring-system interface requirements, documented communication failure scenarios, coordinated updates with the software team, and helped define tests to verify data-loss detection.”

This description identifies:

* The system context
* The activity
* The technical concern
* Collaboration
* The resulting evidence

Only use a description like this if it accurately reflects your work.

### Evidence hierarchy

Useful evidence can include:

1. Approved requirements and specifications.
2. Architecture diagrams and interface definitions.
3. Analysis reports, models, and trade-study records.
4. Verification plans, test procedures, and results.
5. Risk registers and change-impact assessments.
6. Review minutes and documented decisions.
7. Configuration records and release documentation.
8. Stakeholder acceptance records and operational reports.
9. Supervisor or project-lead confirmation of your role.

Not every experience will have all these artifacts. For older projects, you may need to reconstruct a truthful narrative from available records and supervisor confirmation.

Protect confidential information. Do not include proprietary designs, restricted technical data, customer secrets, credentials, or sensitive project details in an application portfolio without authorization.

## 5. The STAR-E Method for Experience Descriptions

A useful structure for explaining experience is **STAR-E**:

* **S — Situation:** What system or project was involved?
* **T — Task:** What responsibility were you assigned?
* **A — Action:** What did you personally do?
* **R — Result:** What changed or was delivered?
* **E — Evidence:** What record, measurement, test, review, or confirmation supports the result?

### Example

**Situation:** A monitoring service needed to exchange data with a backend API.

**Task:** Support the definition and testing of the interface.

**Action:** Reviewed data fields, documented expected responses and error cases, and helped create API tests.

**Result:** The team had a clearer interface contract and repeatable checks for expected behavior.

**Evidence:** Interface documentation, test cases, execution results, and project-lead confirmation.

The result should be specific and truthful. Do not invent performance improvements, ownership, approvals, or metrics.

## 6. Distinguish Participation, Contribution, and Ownership

A common experience-writing mistake is to overstate responsibility.

| Wording     | Meaning                                                     |
| ----------- | ----------------------------------------------------------- |
| Observed    | Watched or learned from an activity                         |
| Assisted    | Supported work led by another person                        |
| Contributed | Completed a defined part of the work                        |
| Developed   | Created a deliverable or solution                           |
| Coordinated | Organized work among people or technical areas              |
| Led         | Directed the activity and its execution                     |
| Approved    | Had formal authority to authorize a decision or deliverable |

Choose verbs that match your actual role.

For example, if a senior engineer approved the architecture and you prepared diagrams, say that you **prepared architecture diagrams under supervision**, not that you independently owned the architecture.

Honest descriptions are more defensible in applications, reference checks, and technical interviews.

## 7. Mapping Academic Projects and Early-Career Work

Academic, internship, laboratory, and supervised project experience can demonstrate systems engineering knowledge and skills. However, whether particular experience counts toward certification eligibility depends on the current official rules and the nature of the work.

For each project, record:

* Project name and context
* Dates and duration
* Academic, internship, or professional status
* Team size and your role
* System boundary and principal interfaces
* Requirements and constraints
* Methods and tools used
* Deliverables produced
* Decisions you influenced
* Results and supporting evidence
* Supervisor or reference, where appropriate
* Any gaps between academic exercise and real operational deployment

### Academic project example

Suppose a student team develops a connected healthcare-monitoring prototype.

Possible evidence includes:

* Stakeholder needs analysis
* Functional and non-functional requirements
* Hardware/software interface definitions
* Model or algorithm evaluation
* API integration tests
* Verification results
* Risk analysis
* Final demonstration and stakeholder feedback

If the project was a prototype, do not describe it as a deployed clinical system unless that is true. If you evaluated a model in a laboratory, do not claim clinical validation unless the appropriate validation was performed.

The quality of an experience description depends on accurate scope, personal contribution, and evidence—not on making the project sound larger than it was.

### Optional self-assessment scale

For personal development planning, use a simple scale:

* **0 — No evidence:** No relevant example identified.
* **1 — Awareness:** Understand the concept or observed the activity.
* **2 — Assisted:** Supported a relevant activity under supervision.
* **3 — Contributed:** Completed a defined part of the work.
* **4 — Independently applied:** Performed the activity with appropriate judgment and limited supervision.
* **5 — Led or improved:** Led the activity, handled complex decisions, or improved the approach.

This scale is for your own learning and must not be presented as an official INCOSE competency score.

A low score does not necessarily mean that you lack knowledge. It may mean you need a better example, stronger evidence, or additional practical experience.

## 9. Build an Experience Inventory

Before writing application narratives, create a complete inventory of projects and roles.

Suggested fields:

| Field                | What to record                                           |
| -------------------- | -------------------------------------------------------- |
| Project or role      | Recognizable project title or position                   |
| Organization         | Employer, university, or project sponsor                 |
| Dates                | Start and end dates                                      |
| Engagement type      | Employment, internship, academic project, volunteer work |
| System context       | Purpose, users, environment, and boundaries              |
| Your responsibility  | Actual role and reporting relationship                   |
| Technical activities | Tasks you personally performed                           |
| Deliverables         | Artifacts or outputs you produced                        |
| Outcomes             | Results supported by evidence                            |
| Competencies         | Relevant categories from the mapping framework           |
| Evidence location    | Authorized document or reference                         |
| Confirmation         | Supervisor or project contact, if appropriate            |
| Eligibility status   | Confirm separately against current official rules        |

Maintain both a detailed private inventory and a shorter version suitable for an application or CV.

## 10. Experience Mapping for Different Roles

Systems engineering activities can appear under many job titles. A title alone does not determine the relevance of the work.

### IT infrastructure and networking

Potentially relevant activities include:

* Capturing service and availability needs.
* Documenting network requirements and interfaces.
* Evaluating network architecture alternatives.
* Planning integration and migration.
* Defining acceptance tests.
* Analyzing service risks and dependencies.
* Coordinating configuration changes.
* Validating service behavior after deployment.

Routine troubleshooting may build valuable technical expertise, but it is not automatically equivalent to full systems engineering experience. Explain the engineering activities involved and verify eligibility against the official criteria.

### Software and AI systems

Potentially relevant activities include:

* Translating user needs into system requirements.
* Defining API and data interfaces.
* Comparing architecture alternatives.
* Establishing performance and resource constraints.
* Planning integration and verification.
* Evaluating model behavior under defined conditions.
* Addressing reliability, security, safety, and data quality.
* Managing releases and configuration changes.

Training a model alone does not establish that the complete system has been validated for its intended operational use.

### Data and analytics systems

Potentially relevant activities include:

* Defining stakeholder questions and decision needs.
* Establishing data-quality requirements.
* Designing data pipelines and interfaces.
* Evaluating end-to-end performance.
* Addressing access control and data retention.
* Verifying calculations and data transformations.
* Validating whether outputs support the intended decisions.
* Planning monitoring, recovery, and maintenance.

## 11. Competency Gap Analysis

After mapping your experience, identify the difference between the evidence you currently have and the evidence you would like to develop.

A gap may reflect:

* Limited practical exposure
* A missing artifact or weak documentation
* Unclear personal contribution
* Lack of quantitative evidence
* Limited experience with complex interfaces
* Little exposure to validation or life-cycle support
* Unfamiliarity with a particular method or discipline

### Example development plan

| Gap                        | Development action                                             | Evidence to create                        |
| -------------------------- | -------------------------------------------------------------- | ----------------------------------------- |
| Requirements traceability  | Build a requirements-to-test traceability matrix for a project | Requirements and test mapping             |
| Architecture trade studies | Compare two realistic architecture alternatives                | Decision matrix and rationale             |
| Risk analysis              | Conduct a structured risk review                               | Risk register and mitigation plan         |
| Verification planning      | Define requirement-based test cases                            | Verification matrix and results           |
| Validation                 | Evaluate a prototype with representative users                 | Acceptance criteria and evaluation report |
| Specialty engineering      | Perform a justified FMEA or usability review                   | Analysis report and recommended actions   |
| Change management          | Practice impact analysis for a proposed change                 | Change request and impact record          |

Use a real or clearly identified learning project. Do not label a simulated exercise as paid professional experience.

## 12. Interview Preparation Using Competency Evidence

Interviewers may ask how you handled an unclear requirement, a technical conflict, a failed test, a change request, or a difficult interface.

Prepare several truthful examples covering different competency areas.

### Example interview question: “Tell me about a technical trade-off you evaluated.”

A strong answer should explain:

1. The decision that needed to be made.
2. The stakeholder needs and mandatory constraints.
3. The alternatives considered.
4. The criteria and evidence used.
5. The risks and compromises identified.
6. The decision, your role, and the outcome.
7. What you learned or would improve.

Avoid saying “I selected the best design” without explaining how you evaluated alternatives and justified the decision.

### Example interview question: “How do you know a system is ready for delivery?”

A sound answer should distinguish:

* Verification evidence against baselined requirements
* Validation evidence against stakeholder needs and intended use
* Open defects and residual risks
* Interface and integration status
* Operational and support readiness
* Required approvals and acceptance criteria

The exact release decision process depends on the project's governance and risk level.

## 14. Exercises with Suggested Answers

### Exercise 1 — Classify the evidence

A candidate says, “I attended an architecture review.”

What additional information is needed to demonstrate competency?

**Suggested answer:** Establish whether the candidate observed, contributed, prepared analysis, identified issues, evaluated alternatives, or made a documented decision. Attendance alone does not demonstrate the depth of the person's contribution.

### Exercise 2 — Improve a weak experience statement

Rewrite: “Worked on testing.”

**Suggested answer:** A stronger version, if factually accurate, might be: “Prepared test cases mapped to specified interface requirements, executed them against the integrated prototype, recorded failures, and supported defect retesting.” It identifies activities and evidence without claiming more than the candidate did.

### Exercise 3 — Academic versus professional experience

A university team built a prototype that was never deployed. How should it be described?

**Suggested answer:** Identify it as an academic prototype, describe the system scope and individual contribution, and report the tests and demonstrations actually completed. Do not imply production deployment or operational validation.

### Exercise 4 — Avoid double-counting

One integration activity involved requirements, interfaces, testing, and risk.

How should it be recorded?

**Suggested answer:** Record the activity once in the experience inventory and map its distinct evidence to relevant competency categories. Do not count it as four separate projects or assume each category establishes eligibility independently.

### Exercise 5 — Find the gap

A candidate has strong design experience but no examples of stakeholder validation.

What should the candidate do?

**Suggested answer:** Seek a legitimate opportunity to define stakeholder acceptance criteria and evaluate a system in its intended context. Record the method, participants, results, limitations, and personal contribution.

### Exercise 6 — Assess a trade study

A candidate selected a design because it had the lowest cost.

What is missing?

**Suggested answer:** The decision needs requirements and constraints, evaluation criteria, evidence about performance and risk, analysis of alternatives, and documented rationale. Lowest cost alone may not satisfy mandatory requirements.

### Exercise 7 — Identify weak evidence

A candidate reports a 40% improvement but has no baseline or measurement record.

How should the claim be handled?

**Suggested answer:** Find reliable supporting data and explain the measurement method, or remove the numerical claim. A precise number without evidence can undermine credibility.

### Exercise 8 — Map IT work

An IT technician configures VLANs and helps migrate a service to a new network.

Which systems engineering activities might be relevant?

**Suggested answer:** Depending on the actual work, relevant activities could include requirements analysis, interface definition, architecture evaluation, migration planning, risk management, configuration control, integration, verification, and operational validation. The technical task alone does not automatically establish that every activity occurred.

### Exercise 9 — Demonstrate systems thinking

A software update improves response time but increases memory use and introduces a new failure mode.

What competency does the response demonstrate?

**Suggested answer:** Systems thinking and trade-off analysis: evaluate performance, resource constraints, reliability, interfaces, and operational consequences together. Record the analysis and resulting decision.

### Exercise 10 — Check certification eligibility

A candidate has completed several courses and personal projects but has limited employment experience.

Can the candidate assume that the CSEP experience requirement is satisfied?

**Suggested answer:** No. Courses and projects may build knowledge and provide evidence of capability, but eligibility must be assessed using the current official INCOSE rules and the candidate's actual experience.

## 15. Original Exam-Style Practice Questions

*These questions are independently written for study practice and are not official INCOSE examination questions.*

### Question 1

What is the primary purpose of competency mapping?

A. To replace the official certification application
B. To organize experience and evidence against relevant competency areas
C. To guarantee that a candidate qualifies
D. To convert every technical task into systems engineering experience

**Answer: B.** Mapping helps organize evidence and identify gaps. It does not replace official eligibility rules or guarantee certification.

### Question 2

Which experience statement is strongest?

A. “I worked with a network.”
B. “I am familiar with requirements.”
C. “I documented interface requirements, mapped them to integration tests, and recorded the results.”
D. “I was responsible for everything.”

**Answer: C.** It describes specific activities and evidence. The statement must still accurately represent the candidate's contribution.

### Question 3

A candidate observed a risk review but did not participate in the analysis. What is the most accurate claim?

A. The candidate led the risk analysis.
B. The candidate independently approved the risk response.
C. The candidate observed the review and learned about the process.
D. The candidate eliminated the project's risks.

**Answer: C.** The description should reflect the actual level of participation.

### Question 4

Which item is the strongest direct evidence that requirements were verified?

A. A general statement that testing occurred
B. A requirement-linked test procedure and recorded results
C. A project title
D. A list of programming languages

**Answer: B.** Traceable procedures and recorded results provide evidence of verification, subject to the test's adequacy and acceptance criteria.

### Question 5

What should a candidate do when a project outcome cannot be supported by a reliable measurement?

A. Invent a reasonable percentage.
B. Present the estimate as a confirmed result.
C. Remove or qualify the claim and explain only what can be supported.
D. Attribute the outcome to the whole team without explanation.

**Answer: C.** Accurate and defensible claims are more valuable than unsupported numerical precision.

### Question 6

Which statement best distinguishes verification from validation?

A. Verification checks conformance to specified requirements; validation evaluates whether the system meets stakeholder needs in its intended context.
B. Verification is only for hardware; validation is only for software.
C. Verification and validation are interchangeable terms.
D. Validation eliminates the need for requirements.

**Answer: A.** Both are necessary, and their scope and methods depend on the system and life-cycle context.

### Question 7

A candidate has completed a relevant course but has not applied the method to a project. What can be concluded?

A. The candidate has demonstrated professional competency in the method.
B. The candidate has evidence of learning, but practical application has not yet been demonstrated.
C. The candidate automatically satisfies experience requirements.
D. The candidate is ineligible for all certification programs.

**Answer: B.** Learning and demonstrated application are different. Official eligibility depends on the applicable certification rules.

### Question 8

Why is a record of personal contribution important?

A. It proves the candidate completed the entire project.
B. It distinguishes the candidate's work from the team's collective output.
C. It removes the need for references.
D. It makes supporting evidence unnecessary.

**Answer: B.** Clear attribution makes experience claims more accurate and easier to evaluate.

### Question 9

A candidate maps one integration activity to several competencies. What is the best practice?

A. Count the activity as several separate projects.
B. Record the activity once and map its distinct evidence to the relevant areas.
C. Remove the activity from the record.
D. Assume each mapped competency independently satisfies eligibility requirements.

**Answer: B.** One activity can provide evidence across several competencies without becoming multiple separate experiences.

### Question 10

Which is the most appropriate way to determine whether a candidate meets CSEP experience requirements?

A. Use a personal spreadsheet alone.
B. Compare the candidate's record against the current official INCOSE requirements and application guidance.
C. Count only the number of certificates earned.
D. Assume all technical employment qualifies.

**Answer: B.** The current official certification materials govern eligibility.

## 16. Revision Notes

* Eligibility and competency are related but distinct.
* Always consult current official INCOSE rules for certification eligibility.
* A competency map is a personal planning tool, not an official scoring scheme.
* Strong experience evidence explains context, personal contribution, result, and supporting records.
* Distinguish observation, assistance, contribution, leadership, and formal approval.
* Academic projects can demonstrate learning and technical activities, but describe their scope accurately.
* Map activities to competencies without double-counting projects.
* Use traceable evidence wherever possible.
* Protect confidential information and avoid unsupported claims.
* Identify gaps and pursue practical development opportunities.
* Prepare interview examples that explain the problem, decision process, evidence, outcome, and lessons learned.
